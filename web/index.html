How it works

Five steps, in this order. The whole workflow is pipeline/runner.py, about a hundred lines of Python.

  1. Chunk

    The document is split into overlapping pieces, so a fact on a boundary is never lost.

  2. Extract

    Each chunk is reduced to its facts and its exact numbers. This is the map half of map-reduce.

  3. Plan

    A planner decides which outputs this document can honestly support, and how deep to go.

  4. Write & critique

    A writer drafts the output; a critic scores it out of five and names what is wrong.

  5. Repair

    Below four, the draft goes back to the writer with the defects. Twice at most, then it ships flagged.

What it is built with

  • Sarvam V2 chat completions — the writing and critiquing models, with Structured Outputs so replies match a schema.
  • Sarvam /translate — a purpose-built translation model, not a chat prompt, for Indic output.
  • Python — a plain pipeline, no orchestration framework.
  • Streamlit — the full app, with uploads and downloads.
  • HTML, CSS, JavaScript — this page, talking to a FastAPI bridge.
  • SQLite and Supabase — every run logged, for the dashboard.
  • Power BI — quality and cost across runs.
